## Context

2nd-brain started as a Chief of Staff (COS): a journal fed from Telegram, morning briefings, task suggestions, and copies of Google Calendar, Contacts, Tasks and Gmail. It also served content discovery: editorial picks recorded for the socialisn tools. Two things changed:

- **Chief of Staff.** Meta's Muse now works directly with Simon's Gmail, Calendar, Contacts and Tasks, so 2nd-brain no longer needs copies of them or COS features.
- **Content discovery.** Muse and Gemini Spark took this over. socialisn and socialisn2 are deprecated.

The retirement started this week:

- #87 removed `/feed`, the morning briefing, and the Google data nothing used.
- #88 removed the Telegram bot, task suggestions and `/ask`, and made Google Tasks read-only.

## Decision: what 2nd-brain is for

2nd-brain is Simon's private home for three things he creates himself:

1. **Personal thoughts.** The journal, saved from his AI chat sessions with `save_session`.
2. **Published work.** Columns, essays and YouTube episodes, held in `public_artifact`. They are rebuilt from the Gmail "Writing" label, the Drive archive folders, the Substack and WordPress exports, and the YouTube transcript sync.
3. **The Idea Garden** (formerly the Idea Parking Lot), per the brief. It keeps interesting ideas so reliably that they stop nagging him, and it makes them collide through typed links with one-line glosses. An idea enters only when he says "park this", and a link exists only when he says yes.

Any AI assistant he connects (Claude, Meta Muse, Gemini Spark) reaches it through the one MCP server. It stays pull-only: it never pushes, schedules or reminds.

Downstream, the pipeline is **Garden → Subjects → Projects → Shipped**. He promotes episode-shaped ideas to his Google Tasks "Subjects" list, and he or Muse writes the task. Published pieces return to the archive, where `became` links close the loop.

## Guardrails for every phase

- **Data migrations** run when the monolith boots on Railway. Each one starts with `SET LOCAL statement_timeout = 0;` and is idempotent: guarded `DELETE`/`UPDATE`, and `DROP ... IF EXISTS`. (The runner, `src/db/migrate.ts`, also lifts the pool's 10 s limit on its own connection, so a slow schema migration can't fail the boot either. Lock waits keep the 10 s limit, as `lock_timeout`: a migration blocked behind an open transaction fails the boot, which is retried, rather than hanging it while the table's queries queue behind the migration.)
- **A migration that drops a link target table also deletes the `link_edge` rows that point at it,** as migration 024 did for `email_ref`: `person_ref` and `calendar_event_ref` in Phase 3, `task_ref` in Phase 7. `link_edge.target_id` has no foreign key, so these rows outlive the table, and their `explanation` text names the target: a contact's name (for some contacts saved without a name, their email address; see the PR #87 review), an event or task title. Once `get_entry` stops joining the dropped table, it would still return them to personal entries.
- **Before any migration that deletes or drops data,** Simon takes a full Postgres backup and confirms it exists.
- **Ordering.**
  - Code that reads a table changes before the migration that drops it.
  - A migration that adds a column lands before the code that needs it.
  - Railway variables are deleted only after the code no longer reads them.
- **Archive consolidation supersedes legacy rows; it never deletes them.** `idea_link.target_artifact_id` cascades on delete, so deleting would erase confirmed garden links.
- **Exports of retired data go to a private location, never this public repository.**
- **Google scopes shrink only through a revoke-and-reconnect:** remove the app at myaccount.google.com/connections, then reconnect at `/auth/google`. A plain reconnect leaves the earlier, wider grant live at Google. This happens twice: in Phase 3 and in Phase 7.
